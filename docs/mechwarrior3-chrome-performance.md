# MechWarrior 3 Chrome performance investigation

Measured September 14, 2026, on the local Jenkins demo site. The reported
1–2 FPS reproduces in single threaded JIT. Two established contributors are
browser scheduling gaps and CPU work in the emulated graphics stack. A
temporary scheduling change improves throughput substantially but does not
make the game fast.

## Scheduler A/B/A result

Three sequential 30-second measurements in a stationary cockpit view:

| Scheduler | Swaps | FPS | Median interval | 95th percentile interval |
| --- | ---: | ---: | ---: | ---: |
| Existing timeout mode | 47 | 1.56 | 636 ms | 786 ms |
| Temporary immediate mode | 74 | 2.46 | 407 ms | 458 ms |
| Existing timeout mode restored | 52 | 1.73 | 578 ms | 722 ms |

The immediate-mode result is 42% above the restored control and 57% above the
initial control. These are real-time gameplay observations, not deterministic
benchmark replays. Workloads remain close: 642–664 draw calls per swap and
approximately five readbacks per swap across the three phases.

The existing scheduler is selected at
`source/sdl/emscripten/mainloop.cpp:129`:

```cpp
emscripten_set_main_loop_timing(EM_TIMING_SETTIMEOUT, 1);
```

The same loop yields after approximately 10 ms of work, or after presentation
(`mainloop.cpp:185`). The generated Emscripten runner reschedules with
`setTimeout`. Its argument does not guarantee that the callback runs after
one millisecond.

A separate instrumented 10-second sample per mode measured actual gaps:

| Scheduler | Callbacks | Active time | Time between callbacks | Mean gap |
| --- | ---: | ---: | ---: | ---: |
| Timeout | 339 | 5.88 s | 4.13 s | 12.23 ms |
| Immediate | 568 | 9.90 s | 0.11 s | 0.19 ms |

The test changed only the live page's existing Emscripten setting with
`_emscripten_set_main_loop_timing(2, 0)` and restored `(0, 1)`. Mode 2 uses the
runtime's message-based immediate scheduler on this browser. Both scheduling
controls preserve yields to the browser; no guest workload was skipped.
The immediate mode has not been qualified across browsers, audio, input,
power consumption, or the full graphics test suite. No production scheduler
change was made.

## CPU and graphics costs

A separate 32.3-second CPU sample, from an earlier stationary cockpit view,
has these approximate self-time shares of elapsed time:

| Sample category | Share |
| --- | ---: |
| Boxedwine runtime | 24.6% |
| Emulated WineD3D code | 23.6% |
| Browser idle | 24.6% |
| Remaining guest libraries, game code, JS and browser calls | 27.2% |

Within the first category, `wasmStartJITOp` alone accounts for 14.7% of elapsed
time, and `wasmHelper_fetchNextOp` for 3.3%. These are block-execution/dispatch
hotspots, not evidence that initial JIT compilation explains the sustained
slowdown. The largest named WineD3D hotspots are:

- `wined3d_texture_gl_read_pixels_webgl_color`: 3.53% self time.
- `wined3d_texture_gl_readback_depth_webgl`: 2.70%.
- `wined3d_device_apply_stateblock`: 1.73%.
- `wined3d_texture_gl_convert_webgl_row`: 1.34%.

The exact DLL's COFF symbols map the JIT names' file offsets to functions.
JIT dispatch time cannot be attributed precisely to individual guest callers
using this sample; these percentages are not total costs of those operations.

Timing WebGL calls in the first sample recorded 1.72 s inside those calls out
of 32.58 s measured. `readPixels` accounts for 0.52 s. That argues against
GPU waiting being the dominant cost in this run. Hardware rendering is active.
These timings include browser API execution and synchronization, not a
separate GPU timer query.

The later frame-count samples record about five full 640×480 RGBA8 readbacks
per swap, each with a 1,228,800-byte destination: approximately 6.14 MB and
1.54 million pixels per frame. Wine's WebGL compatibility helpers then process
color/depth pixels on the emulated x86 CPU. The drawing path also makes roughly
650 draw calls and 3,200–3,300 measured scalar/vector uniform calls per frame.

Relevant Wine sources are preserved in
`tmp/cc54/p8-presentation-build/candidate-source/dlls/wined3d/texture_gl.c`:
color readback at 2342, depth readback at 2588, and uploads at 1688 onward.
Versioned patches include
`tools/d3dToWebGL/webgl-depth-readback-against-wine-11.0.patch` and
`tools/d3dToWebGL/webgl-rgb10-transfers-against-wine-11.0.patch`.

One follow-up hypothesis is unnecessary synchronization of GPU and system
memory copies. In the preserved `dlls/ddraw/surface.c:2064` depth-fill path,
the WebGL branch clears the GPU target and then also clears its system-memory
copy. Trace the actual callers and rectangle coverage before changing this:
the current evidence does not prove which application calls cause each of the
five readbacks or which copies can safely be omitted.

## Measurement details and limits

FPS counts `GLctx.flush()` calls. A captured stack verifies that the calls
come from `KOpenGLSdl::glSwapBuffers` through `gl_common_EglSwapBuffers`.
For this single-threaded launch, the WebGL context renders directly into
`#canvas`. The first attempted canvas-copy observer counted zero because it
watched `drawImage`/bitmap copies to `#boxedwine-webgl-canvas-0`; that counter
is unsupported for this path and is not used as an FPS result. Do not use
`requestAnimationFrame` callback counts as game FPS either.

The first CPU sample enabled timing of WebGL calls. The A/B/A samples instead
used lightweight counters for swaps, draws, selected uniforms and readbacks,
without CPU sampling or per-call duration measurements. Each measurement
records visibility, focus, and scheduler settings. No network downloads or
game startup were part of the measured phases.

An optional readback-origin probe run after all these measurements failed:
it tried to convert an entire Emscripten heap view to an array before slicing
four elements, and threw `RangeError`. Its saved empty/partial event sequence
is invalid and excluded. The earlier raw measurements were already saved.
Temporary hooks were removed, the timeout scheduler was verified restored,
and the stopped test game was unloaded back to the catalog. This was an
instrumentation failure, not a new game/runtime failure or a clean guest-exit
test. A follow-up must slice/bound views before copying and contain probe
exceptions so they cannot escape into the emulator.

No runtime, Wine DLL, deployed page, installed container, or source code was
changed. Normal pilot creation may have saved `bw` in this game's browser
storage. No commit, staging, publishing, or deployment was performed.

The expensive float-to-integer conversion isolated here belongs to Wine's
WebGL depth-readback helper. The original demo's separate WebGL `wined3d.dll`
uses x87 for this loop, as does the retained color-optimized DLL. This does

### Fresh gameplay and JIT behavior

The retained clean build measured 2.298 FPS over 30 seconds, with about 1235
draws and four readbacks per complete frame. A second gameplay window with
Chrome CPU sampling enabled measured 2.165 FPS at about 1240 draws per frame.

Unresolved generated guest code remains 8.83%; ELF modules are not fully
resolved to individual functions. Runtime dispatch self time cannot be
assigned precisely to each Wine or game caller from this profile.

A separate runtime enabled the existing `BOXEDWINE_WASM_JIT_PROFILE` counters.
Only the first and last periodic records wholly inside gameplay were
differenced, excluding startup. Across approximately 30 seconds:

- 262.13 million sampled/scaled block-dispatch entries were recorded.
- 99.970% of measured next-target transitions found JIT code; 99.863% of
  `fetchNext` targets also found JIT code.
- Mean execution-chain length was about 1133 blocks. About 53% of chains
  stopped at the 2048-block cap. This cap differs from the previously tested
  64-iteration direct-loop budget.
- No table-slot misses or memory-array refreshes occurred. Inline memory

- 806 additional blocks were compiled. The reported 46.6 average operations

This argues against frequent interpreter fallback as the primary problem.
It does not make dispatch free: the clean CPU profile still identifies it
as a major cost. The instrumented runtime measured only 1.532 FPS and must
not be used as a production speed comparison. Its sampled `time_us` fields
also exceed elapsed time, involve overlapping intervals and clock overhead,
and are unsuitable for wall-time attribution. Only counter counts and ratios

### All four readback callers identified

A bounded diagnostic Wine DLL captured 40 complete readback records using
the normal runtime, with JIT counters and Chrome CPU sampling disabled.
The sequence was depth/color/color/color repeated ten times. Every download
was 640 by 480; all depth operations succeeded. Exact DLL symbols and loaded
module bases resolved the captured guest return addresses.

| Operation | Occurrences per frame | Median GPU read | Median CPU conversion |
| --- | ---: | ---: | ---: |
| RGB565 color, format 116 | 3 | 5 ms | 3 ms |
| D16 depth, format 85 | 1 | 3 ms | 22 ms |

Depth setup additionally took a median 2 ms and its tail 0.5 ms. Timers have
roughly 1 ms granularity; sums of component medians are approximate. Together
these helpers account for roughly 50 ms of a roughly 435 ms frame, so removing
their work alone would not explain or eliminate the entire slowdown.

The color stack is `ddraw_surface4_Lock` -> `surface_lock` -> resource map ->
texture location load -> color readback. The depth stack is
`ddraw_surface1_Blt` -> `ddraw_surface_blt` ->
`wined3d_device_context_clear_sysmem_texture` -> `cpu_blitter_clear_texture`
-> texture location load -> depth readback.

The DirectDraw WebGL depth-fill branch first clears the GPU render target,
then eagerly clears the default/system-memory texture and marks both copies
current. This is the branch in
`tools/d3dToWebGL/webgl-directdraw-runtime-presentation-against-wine-11.0.patch`
around line 1063. The trace confirms that this second clear triggers the
remaining depth download. The retained full-surface-clear optimization already
bypasses location loading for a complete clear. Thus the remaining path
suggests partial coverage; the actual rectangle was not captured and this
remains an inference from the branch conditions.

The trace ends at the exported DirectDraw calls. It does not identify game
call sites, lock flags, lock rectangles, or whether the three color locks
need old pixels. Do not remove synchronization without checking those facts
and the existing depth-lock, stencil, and partial-clear behavior. The code
establishes eager CPU synchronization, but its original necessity has not
been established by this diagnostic run.

`readback-analysis.json` contains every resolved stack and timing. The
diagnostic root with tracing unarmed measured 2.298 FPS and about 1246 draws
per frame, matching the clean build's range. An earlier diagnostic wrote to
guest stderr and produced no caller logs because the GUI game had no usable
stderr stream; that failed capture is preserved and excluded. The successful
version uses explicit `BW_MECH_READ_*` Wine log markers, outside the measured
conversion interval. Those intentional markers are not game errors.

### Identical conversion loops through x86 JIT and direct Wasm

The literal color/depth loop bodies were extracted into a standalone harness
and compiled as Win32 x86 and direct Wasm. Win32 variants used `-O3` with
default x87 or explicit `-msse2 -mfpmath=sse`. Direct Wasm used Emscripten
`-O3 -msimd128`. These compare practical compiled kernels, not the isolated
cost of a single emulated instruction. No fast-math option was added.

The final x87/SSE comparison used the same 200-image warmup and three timed
trials of 20 images. Direct Wasm used five trials of 200 images. Values below
are median milliseconds per 640 by 480 image.

| Extracted conversion | x86 JIT, x87 | x86 JIT, SSE2 | Direct Wasm |
| --- | ---: | ---: | ---: |
| RGBA8 to RGB565 | 2.00 | 1.00 | 0.152 |
| Float depth to D16 | 19.90 | 15.85 | 0.654 |
| Float depth to D24X8 | 20.30 | 20.40 | 0.855 |
| Float depth to packed D24S8 depth bits | 18.55 | 16.35 | 0.850 |

All variants matched output checksums for all four fixed-seed input images,
including row padding. This is correctness evidence for the measured inputs,
not exhaustive floating-point boundary coverage or graphics qualification.
Raw trials are retained, including a 31.7 ms x87 packed-depth outlier.
Native Windows x86 reference outputs also matched.

SSE lowers D16 conversion time by about 20%, but gives no material improvement
for D24X8 in this test. The SSE disassembly still uses a long unsigned
float-to-integer sequence, including packed operations and `cvttpd2dq`;
packed instructions here do not establish that multiple pixels are processed
together. An initial disassembly validator expected scalar `cvttsd2si` and
rejected that expectation after successful compilation. The corrected
validator checks the actual SSE instructions and matching outputs.

The SSE D16 kernel is still about 24 times slower than its direct-Wasm
counterpart. This demonstrates substantial overhead for this translated
