# Native macOS preview

Demo recipes and icons come from a [shared pinned catalog ZIP](../../../../resources/DEMO_CATALOG.md), fetched during the Xcode build. The exact verified cache supports offline builds. A local build with no usable catalog continues without demos; Jenkins requires the pinned package. No catalog fallback is checked into Git.

This is the first working native launcher, aimed at people bringing a few familiar Windows apps or games to their Mac. It is a development preview, not an App Store submission.

## Build and run

About Boxedwine uses the emulator's public version from `BOXEDWINE_VERSION_DISPLAY` in `include/boxedwine.h` and offers a GitHub issue link. Both Mac targets generate their versioned Info.plist from that definition during the build; there is no separate native UI version to update. `CURRENT_PROJECT_VERSION` remains the independent Xcode build number. Report an Issue is also available in the Help menu.

Install the Mac dependencies described in the repository's `BUILD.md`. The packaged preview currently targets **Apple Silicon and macOS 15 or later**, using Swift 6. Mac builds use native OpenGL and no longer include software Mesa or its dependencies. The existing deployment target remains unchanged; supporting older macOS or Intel requires separate dependency and runtime verification. The standalone Swift library still targets macOS 13. The app has been built and exercised with Xcode 26.5; testing on macOS 15 itself remains outstanding.

From the repository root:

```sh
sh project/mac-xcode/buildNative.sh /absolute/path/to/Boxedwine-Wine-filesystem.zip
```

The output is `project/mac-xcode/bin/native-build/Build/Products/Debug/Boxedwine.app`. Use `--configuration Release` before the Wine path for an optimized local preview in the corresponding `Release` directory. The `BoxedwineUI` shared scheme builds the interface and its `Boxedwine` emulator dependency automatically. The old Mac launcher target has been replaced; the existing test and automation targets remain available.

The optional first argument bundles an existing Boxedwine Wine filesystem ZIP as `Resources/WindowsSupport/wine.zip`. The build runs the same package validator used by the native app before bundling it. Without that argument, choose a Wine version from the bundled catalog in Settings or Add App. Required downloads are disclosed before they begin.

These targets use ad-hoc signing for local development with explicit Hardened Runtime flags. Debug uses unsandboxed development entitlements with debugger attachment enabled for both processes; Sandbox and Release keep sandboxing and omit the debugger entitlement. The bundle preparation phase signs SDL's nested hidapi framework before signing SDL and the enclosing app, and clears retired Mesa and obsolete Intel C++ libraries from incremental outputs. The automation target also omits software Mesa and cleans these leftovers. Vendored input binaries are unchanged. SDL/hidapi and MoltenVK remain included where used; see the [dependency audit and removal results](MAC_LIBRARY_DEPENDENCIES.md). Configure team signing and provisioning separately for distribution. The runtime currently retains the existing JIT and library-validation exceptions; minimize and validate those against the chosen release build before submission.

The build script audits its completed bundle and fails on packaging errors. Its JSON inventory is written beside the derived build output as `native-audit-Debug.json`, `native-audit-Sandbox.json`, or `native-audit-Release.json`. It accepts Xcode build-setting overrides after the optional Wine path (use `""` for no Wine); action/output-location overrides require using Xcode directly and auditing that output separately. See [Release preparation](RELEASE.md) for commands, measured constraints, license-material gaps, and App Store review questions. Passing this audit does not make an App Store submission ready.

Debug uses `ENABLE_DEBUG_DYLIB=NO`: the ad-hoc hardened launcher cannot load Xcode's separate ad-hoc Swift debug dylib under library validation because they have no shared Team ID. This preserves the launcher's library validation and keeps ordinary unoptimized Debug code in its executable. Xcode's debug-dylib preview mechanism is unavailable in this configuration.

## Targets and debugging

There are two main application targets: `BoxedwineUI` builds this SwiftUI launcher, and `Boxedwine` builds the emulator with the old UI disabled on Mac. The UI embeds `BoxedwineEngine.app` in `Contents/Helpers` and starts its executable with the existing argument, log, and stdin protocol. The visible product is **Boxedwine.app** and retains its bundle identifier and saved library. Its executable is `BoxedwineUI`, so the debugger can still wait specifically for the `Boxedwine` emulator process. `BOXEDWINE_UI_LAUNCH_IN_PROCESS` continues to belong to the older UI path on other builds; the native UI uses separate processes in every configuration.

| Configuration / scheme | Purpose |
| --- | --- |
| Debug / **BoxedwineUI** | Debug the UI. Both processes are unsandboxed and permit debugger attachment; Swift and C++ optimization are disabled. |
| Debug / **Boxedwine** | Builds the complete UI bundle, then waits for an emulator launched through that UI. |
| Sandbox / **BoxedwineUI-Sandbox** | Run the packaged sandbox behavior, with an optimized emulator and no debugger attachment. |
| Release / Archive from **BoxedwineUI** | Optimized UI and emulator, with the packaged sandbox and no debugger entitlement. Distribution signing remains separate setup. |

To debug an already-running Windows app, run the Debug UI, launch the app, then use **Debug → Attach to Process** and select its `Boxedwine` process. Use its PID if several apps are running. C++ breakpoints, threads, and variables belong to that process; SwiftUI breakpoints belong to `BoxedwineUI`'s executable. Xcode can keep separate debugging sessions for the UI and emulator.

For startup debugging, run the Debug UI, select the **Boxedwine** scheme and Run, then launch the Windows app from the UI. The scheme waits for the next `Boxedwine` process. For a guaranteed pause before `boxedmain`, enable the disabled `BOXEDWINE_WAIT_FOR_DEBUGGER=1` environment variable in the **BoxedwineUI** scheme's Run → Arguments settings and restart the UI. Every newly launched helper then logs its PID and waits for attachment. Stop or a closed launcher pipe cancels the wait. Pending Wine preparation may launch a helper before the game; attach to that helper or finish preparation before enabling the pause. The pause is compiled out of Sandbox and Release.

Debug uses the same saved library under `~/Library/Containers/org.boxedwine.native/Data/Library/Application Support/BoxedwineNative`. Close other UI copies before opening it; a lifetime file lock prevents updated builds from editing it concurrently. Older previews do not participate in this lock. For an isolated development library, set `BOXEDWINE_LIBRARY_DIRECTORY` to an absolute directory in the UI scheme's environment; Sandbox and Release ignore this override. Unsandboxed debugging does not exercise App Sandbox permissions, so use the Sandbox scheme for permission and packaging checks.

Apple documents that `get-task-allow` is incompatible with helper sandbox inheritance in [Embedding a command-line tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app). These configurations keep the development and packaged entitlements separate on the same two targets. The bundle audit verifies the selected configuration and rejects mixed or missing entitlements and obsolete embedded helpers.

The same reveal behavior applies to restored apps, Wine test copies, and Show in Library. Scroll requests are consumed once and respect Reduce Motion; ordinary card selection and background updates do not recenter the grid.
- Native File/View menu actions and keyboard shortcuts that follow the visible app selection; built-in Help for demos, imports, saves, troubleshooting and shortcuts.
- A bundled, searchable Demos catalog with local icons, verified downloads, portable ZIP and EXE/MSI installer recipes, cancellation, and pinned shared Wine packages. The catalog now contains 34 entries with typed compatibility settings and assigned Wine 9/11 packages; see [Catalog authoring](DEMO_CATALOG.md) and [Demo coverage](DEMO_COVERAGE.md).
- Portable app-folder import with Windows executable discovery.
- [Boxedwine arguments](BOXEDWINE_ARGUMENTS.md) under Advanced for validated per-app runtime options before `/bin/wine`, with a supported-option reference and a separate app argument field.
- A per-app Windows-version choice before importing or installing, also available in App Settings. Demos prefill their recipe’s version; see [Windows compatibility](WINDOWS_COMPATIBILITY.md).
- A per-app OpenGL backend picker under App Settings → Advanced: Wine’s default, GLX, or EGL. Changes are applied through Wine and verified before the next app or installer launch; Alice retains its demo’s GLX choice. See [OpenGL backend selection](WINDOWS_COMPATIBILITY.md#opengl-backend-selection).
- A Wine renderer picker in Advanced settings exposes the demo’s GDI/OpenGL choice and allows an override or reset to Wine’s default. Half-Life can use GDI for menus while its own video setting uses OpenGL for gameplay. See [Wine renderer selection](WINDOWS_COMPATIBILITY.md#wine-renderer-selection).
- Progress and cancellation for app folders, installers, and imported Windows-support packages, including cancellation within large individual files.
- Windows-support validation, default Wine/version/source details, and a single Choose Wine Version control in Settings.
- Named test copies that use their own Wine version while preserving the original app and library default.
- A searchable program chooser after imports and installer exits, with program names, icons, and paths. Setup/removal tools remain available in a separate disclosure. A single ordinary program can be suggested; ambiguous choices and folders containing only maintenance tools require selection. Suggested programs are not launched automatically.
- Self-contained `.exe`/`.msi` installers and complete installer folders with adjacent payloads and nested setup files. Closing an installer is not interpreted as successful installation. Program choices can be revisited from the library or App Settings.
- Embedded Windows app icons in the library and chooser, with native fallback symbols when an icon cannot be read.
- Try Notepad checks Windows support using the configured Wine package, or the release's default catalog package when no library default is available. Missing Wine prompts with its download size before Download & Open; setup is cancellable and saves a shared, pinned package for Notepad. An existing Notepad entry keeps its saved Wine.
- Separate runtime processes, status reporting, Stop / Force Stop, and coordinated launcher shutdown.
- Complete app backups with native save/open dialogs, checksum checks, cancellation, and restoration into a separate entry with its saved Wine package.
- Reversible removal through a Removed Apps list. Restoring preserves the app's Windows environment, launch settings, and saves.
- Per-app storage estimates, explicit permanent deletion from Removed Apps, and recovery of unfinished deletions.
- An Unfinished Work screen for interrupted app imports, Wine imports, backup exports, and restorations, with verified completion or explicit cleanup.

This preview copies imports into its own Application Support directory, under `BoxedwineNative`, inside the `org.boxedwine.native` sandbox. Each library entry has an independent writable Windows root, installer staging directory, and launch log. The existing `org.boxedwine` library is not migrated or modified. App folders must include their supporting files. Installer Folder copies a selected setup folder and its payloads; optical-media emulation and disc swapping remain future work.

Imports first scan for a byte total, then copy regular files in 1 MB chunks on a worker task. The library and Settings show progress and Cancel. Hidden files and empty folders are included; internal symbolic links are rebuilt inside the copied tree, while links outside the selected folder are rejected. A source that changes during copying is rejected when detected by the size/date checks. Cancellation and copy errors remove partial imports, and a failed library save also removes its uncommitted copy. Cleanup failures are reported. Windows-support changes publish a verified immutable package and then atomically save its default reference; apps with pinned packages retain their versions.

Quitting during an import requests cancellation and waits for cleanup (or an already-committing import) before exiting. A forced kill or power failure can leave uncommitted files; the next launch reports journaled operations in Unfinished Work for review.

Removal is an atomic library-record change and is unavailable while an app is running. Files stay in place and are never automatically purged, so Remove from Library does **not** free disk space. A separate Delete action in Removed Apps can permanently erase them after confirmation. Removed Apps supports search and restoration across restarts. Library format 2 stores both active and removed entries; format 1 loads normally and is backed up as `library-v1-backup.json` before the first format 2 save. Older native previews refuse to open format 2 rather than dropping the recovery list. This metadata backup is not a backup of Windows files or saves.

Settings → Library offers **Delete apps immediately**, off by default and saved as a Mac preference. Enabling it changes the library, context-menu, and File-menu removal actions to **Delete Permanently…**, using one confirmation with Cancel and Back Up First. Confirmation atomically records the active app as a deletion in progress before erasing its owned files; cancellation or failure before that save leaves it in the active library. Interrupted deletions remain accessible in Removed Apps for retry. Existing removed apps are never automatically deleted when changing this setting. Removed Apps and its View command hide only when immediate deletion is enabled and the list is empty; the Manage sidebar section hides when neither Removed Apps nor Unfinished Work needs an entry.

The icon reader handles 16-bit Windows NE, PE32 and PE32+ icon groups without loading or executing the file. It bounds offsets, resource traversal, payload sizes, and image dimensions, then uses ImageIO to decode thumbnails. The library, program chooser, and Dock share a selector that ranks valid representations by their original pixel area before generating a thumbnail capped at 128 pixels. A 256×256 image takes precedence over a 128×128 image even though both produce 128×128 thumbnails; equal sizes retain resource order, and decode failures fall back to the next largest image. File reads occur off the main actor; a bounded cache refreshes when the executable's size or modification date changes. Executables over 64 MB and unsupported images currently use the fallback icon. No icons or artwork are downloaded. Format references: [PE resources](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) and [icon groups](https://devblogs.microsoft.com/oldnewthing/20120720-00/?p=7083).

Installed apps use a custom image when selected, then a usable executable icon, then the release’s bundled demo artwork matched by demo ID. This supplies icons for existing MDK and FreeCol installations without reinstalling them. App Settings → Advanced → App icon offers Choose Image and Use Automatic; edits become persistent only with Save. The file picker accepts images readable by ImageIO, including PNG, JPEG, and icon files. Imports run off the main actor, preserve proportions and transparency, and save a centered 256×256 PNG in the app metadata. Source images are bounded to 16 MiB / 64 megapixels and the saved PNG to 300 KiB. The original image file and its security-scoped grant are not retained. Custom artwork follows app backups, recovery, Wine test copies, and Removed Apps, using library/backup/recovery formats 12/8/9 to prevent older previews from silently discarding it. Program chooser rows continue to show each candidate executable’s own icon.

Icon fallback and custom-image validation (2026-09-12): all 210 tests in 25 suites, Debug build, and bundle audit passed. The signed preview displayed MDK and FreeCol’s bundled artwork in the existing library. Advanced settings showed a live custom preview; Cancel preserved the library byte-for-byte, Save changed only the selected app’s icon and library format, and Use Automatic restored the original app records. Tests cover PNG/JPEG proportions and transparent margins, malformed and truncated artwork, icon precedence and Dock output, external-file independence, and backup/recovery/Wine-copy/removal persistence. Evidence: `tmp/native-ui-test/app-icons/`.

NE resource offsets and lengths are scaled by their alignment shift. Image bytes are limited to the exact length declared by the icon group, excluding alignment padding; named and numeric groups share the PE decoder and largest-image selection. Bounds cover resource tables, entry counts, group sizes and payloads. Synthetic NE fixtures exercise 512-byte alignment, indexed transparency, multiple sizes, missing images, duplicate IDs and malformed/truncated data. Bang Bang's actual Windows 3.0 executable yields its 32×32 cannon icon and a 128×128 Dock PNG. The extraction diagnostic is under `tmp/native-ui-test/ne-icons/`.

The Age of Empires trial's group directory reports a 20×62 icon, repeating the DIB's combined image-and-mask height; the actual image is 20×31. The reader accepts this specific legacy height mismatch and normalizes the generated ICO directory to the bitmap's image height. Other dimension mismatches remain invalid, and PNG dimension checks are unchanged. See Microsoft's explanation of [double-height icon bitmaps](https://devblogs.microsoft.com/oldnewthing/20101018-00/?p=12513).

ImageIO also misreads the transparency-mask padding in this icon, creating bands on alternating rows. Uncompressed indexed DIB icons (1, 4 and 8 bits per pixel) now have their palette, DWORD-aligned color rows, and DWORD-aligned AND-mask rows decoded explicitly. The generated ICO embeds lossless PNG with exact alpha; source executables are never modified. Decoded Age of Empires pixels matched the bundled reference PNG in all 2,480 RGBA bytes. Eight focused icon/program tests passed, including exact color/transparency comparisons at widths 17, 20 and 33 across all three indexed depths, invalid palettes, truncated masks, and existing PE/resource/cache checks. The Debug build and eighteen-image audit passed. Library cards, details and the program chooser display icons in a square, matching the old UI. Native visual verification confirmed the Age of Empires icon has no bands and uses the intended square proportions (2026-09-11).

## Menus, keyboard shortcuts and Help

Try Notepad uses Wine’s bundled transparent Notepad artwork in the library, settings, Removed Apps, and Dock. This also applies to existing Notepad entries; a custom icon still takes precedence. The asset and its Wine source/license are in `Resources/AppIcons`.

Running apps use the same custom image → executable icon → demo artwork order in the Dock. Installers and alternate programs use their own executable icon unless the app has a custom image. The launcher prepares a bounded 128×128 PNG off the main actor using the same reader and square presentation as the library. It passes the PNG as per-child launch metadata; the native runtime consumes and clears it after SDL initialization, then uses AppKit’s [`applicationIconImage`](https://developer.apple.com/documentation/appkit/nsapplication/applicationiconimage) on the main thread. This changes only the running process’s icon. The Age of Empires trial’s helmet icon was confirmed in the Dock on the signed, sandboxed preview. It does not modify the signed app bundle, save new command-line options, or copy artwork into each app’s Windows filesystem. The runtime bundles the Boxedwine icon as its final fallback when none of these sources supplies usable artwork. Icon preparation participates in Launching / Stop / shutdown so cancellation cannot start an app later.

Drag a folder, `.exe`, or `.msi` from Finder onto the library grid to open **Add App** with that source selected. The drop area highlights while targeted. Add App retains the release Wine picker, download-size disclosure, and Windows version choice; a drop alone does not download, copy, or execute anything. Add one app at a time. Folders can be added as ready-to-run apps or installer folders. An `.exe` offers the same choice; choosing a ready-to-run app asks for its folder so macOS grants access to supporting files. Cancelling the sheet or either folder/installer picker leaves the library unchanged. ZIP files must be extracted first, and backups still use **Restore App Backup**. File access lasts through the sheet and any asynchronous import, then is released.

Single-click an app card to select it; double-click anywhere on the card to open it. Double-click uses the same guarded action as Open App, offers Choose Program when needed, and does not launch another instance of an app that is already running.

File includes Open App (Command-O), Stop App (Command-period), App Settings (Command-I), Back Up App (Shift-Command-S), and View Launch Log (Shift-Command-L), alongside Add App (Command-N) and restoration. Open becomes Choose Program when needed; Stop becomes Force Stop while a stop is pending. Removal retains its existing confirmation and has no Delete-key shortcut.

Command-F focuses search in the current library section. View offers All Apps, Recently Opened, and Demos with Command-1 through Command-3. Removed Apps and Command-4 appear while the default removal behavior is enabled or removed entries remain. Unfinished Work and Command-5 appear only when recovery needs attention. Actions apply only to an app visible in the current library results. Filtering out the selection hides its details and disables its app commands. Library actions are disabled while a library sheet is open, or while the separate Settings or Help window is focused. Guest windows retain their existing Windows key handling.

Choose Help → Boxedwine Help for the offline getting-started guide and shortcut reference. macOS retains its standard Help-menu search. App cards expose their selection and status to accessibility tools; demo action labels identify the specific demo. This is an initial accessibility improvement, not a completed VoiceOver or Full Keyboard Access audit.

## Choosing a Windows version

If an app requires a particular Windows version, choose it in Add App before selecting the installer or app files. Otherwise keep **Use Wine’s default**. The same choice is available in **App Settings** while the app is stopped. It controls the Windows version the app sees and is separate from the Wine package version.

Changes apply before the next installer or app launch. Demos prefill their configured version. Cancelling leaves the saved choice unchanged, and normal launches preserve later app/winecfg edits. The launcher runs winecfg in a hidden runtime and verifies the result before starting the app. Returning to Wine’s default discovers and applies the package’s initial Windows-version choice. See [Windows compatibility](WINDOWS_COMPATIBILITY.md) for persistence and verification details.

## Choosing Wine before installation

**Add App → Wine version** lists the Wine entries from the release’s bundled `filesV2.xml`: 11.0, 10.0, 9.0, 6.0, 5.0, 4.1, and 3.1 for 26R2. Select a version by name; Boxedwine downloads the matching package when an exact local copy is unavailable. Opening or cancelling the sheet does not download anything. The separate Windows-version picker controls the Windows version the installer/app sees.

All three manual import choices pin an immutable package in the shared Wine library before any Windows-version preparation or installer launch. Downloads use HTTPS and are checked against release byte counts, SHA-256 fingerprints, Wine metadata, and the full ZIP validator. A different package with the same Wine version is not treated as the selected build. Cancelled or failed imports clean their temporary files; ready imports retain their package through the recovery journal. See [Shared Wine storage](SHARED_WINE.md) for migration and package lifetime.

New apps keep their selected Wine after restart, source removal, and library-default changes. Existing entries retain their prior behavior. **Try Another Wine Version…** uses the same release list to make an independent test copy. Demos automatically obtain the version specified by their recipe. Restored backups retain their own Wine regardless of the Add App pickers. See [Wine catalog](WINE_CATALOG.md) for the release snapshot, package fingerprints, and update procedure.

## Running another program for an existing app

Select an app and choose **Run Another Program…** from its details, context menu, or File menu. Installed configuration tools can be selected from the list. **Choose File…** runs an external `.exe` or `.msi` using the same Windows files and exact Wine package. Select the file, then confirm its containing folder in the second macOS panel. Cancelling either panel leaves the chooser and saved app unchanged. The usual executable, original installer, app arguments and Wine reference stay selected; only launch history advances when the process starts. Saved app arguments are not passed to the tool. Pending Windows-version and OpenGL-backend settings are applied first.

The original folder is mounted directly at `/home/username/boxedwine-program`, with that directory as the working directory. This keeps neighboring DLLs, data, and subfolders available, and permits installers to extract files beside themselves. Writes affect the original Mac files. The mount lives only in that runtime session; it is not recorded as a persistent drive or copied into the app. The guest path is under `/home` because Boxedwine's emulated user cannot create files under `/mnt`. MSI files use Wine's `start /wait /unix` entry point.

The selected folder's security scope is retained through package checking, Wine configuration, icon loading, and runtime exit, including cancellation and failure. An implicit-scope bookmark is passed directly to the sandboxed helper, resolved before filesystem setup, and removed from its environment before Wine starts. No bookmark is persisted or added to the command line, and no entitlements are broadened. See Apple's [file access documentation](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) for passing folder access between processes.

Validation: 197 native library tests pass, including external mount arguments, MSI handling, Java bypass, missing or invalid selections, and saved-app preservation. The Debug native bundle passes its 18-image audit. A 32-bit Windows probe launched through the regular UI in the existing Diablo II app loaded an adjacent DLL and nested data file, found Diablo II on its existing C: drive, and wrote a result back to the original Mac folder. Cancelling folder selection preserved the app metadata exactly. Probe sources, output, and launch evidence are under `tmp/native-ui-test/external-program/`. This validates the launch mechanism. nGlide installation and rendering are untested; Glide 3 support is deferred and is not a Mac release requirement.

## Installing from a folder

Choose **Add App → Installer Folder…** for an extracted installer with data files, such as `.cab` or `.bin` files. First select the folder containing the whole installer, then explicitly choose an `.exe` or `.msi` within it. The second panel can select a setup program in a subfolder; a selection outside the first folder is rejected. Cancelling either panel leaves the library unchanged. **Windows Installer…** remains the single-file option, and **App Folder…** is for programs that are ready to run without installation.

Boxedwine copies the complete selected tree, including hidden files and empty directories, to the new app's private `Installer` directory. It mounts that complete copy at `/mnt/installer`, sets the working directory to the selected setup program's containing folder, and launches the selected relative path. This keeps both nearby and parent-folder payloads reachable. Paths and arguments are passed directly, including spaces and Unicode. MSI launches retain the existing Wine `start /wait /unix` handling. The original source folder is not mounted or modified; security-scoped folder access lasts through the copy and is then released.

The installer opens after the copy commits when Windows support is available. Closing it still does not mean installation succeeded: the program chooser only lists executables found in the writable Windows environment, excluding the copied setup media. The copied installer remains available for reruns, and backups, recovery, and Wine test copies retain its whole media tree. No new metadata field or library format is needed; the existing installer path stores the nested relative location. Nested installers that need parent payloads require this updated launcher because earlier previews mounted only the setup program's immediate parent.

Copies support progress and cancellation through the same worker and operation journal as other imports. Escaping host links, special files, invalid selected programs, and recursive copies of the native library are rejected. A changed source file is rejected when detected by the existing size/date checks. This imports files; it does not emulate a CD/DVD drive, volume labels, copy protection, ISO mounting, or multi-disc swapping.

## Storage and permanent deletion

The app details pane and Removed Apps display an estimate of allocated disk space. The details pane also shows logical file sizes. Estimates include the complete app-owned directory: Windows files and saves, copied installer, logs, and any older private Wine ZIP awaiting migration. Shared Wine packages and exported backups are separate. Scans run on worker tasks, cancel when their view disappears, and refresh after file operations or a running app closes. Missing folders and failed scans are displayed explicitly rather than reported as zero bytes.

Counting uses filesystem allocation blocks and deduplicates hard links by device/inode within the app. Host symbolic links are counted as links, without reading their targets. Allocated size is an estimate of this app's storage, not a promise of recovered free space: external hard links, APFS clones, filesystem snapshots, and filesystem accounting can affect what deletion releases. Scans are bounded to one million entries, checked 64-bit totals, and 128 nested folders.

Choose **Removed Apps → Delete…** for permanent deletion. Its confirmation names the app, lists the files it erases, shows the storage estimate, and offers **Cancel**, **Back Up First…**, and **Delete Permanently**. Deletion is available only for removed apps and never starts merely by opening the confirmation. Once confirmed, it cannot be cancelled; the launcher shows progress and waits for completion or failure before quitting. Other library writes and launches are disabled for the operation. Shared Windows support and exported backups are retained.

Before unlinking any file, Boxedwine atomically records `deletionStartedAt` in the removed entry. This introduces library format 4; the previous metadata is backed up before migration, and older previews reject format 4 instead of offering to restore an incomplete environment. Only after file removal succeeds is the record removed. A failed initial metadata save leaves the files and Restore available. A file-removal failure or interruption retains the marker, disables Restore/Back Up, and offers **Finish Deleting…** after reopening. A failed final metadata save is also retryable, even if all files are already gone. Interrupted deletions are never resumed automatically.

File traversal and deletion use directory descriptors anchored to the library's `Applications/<UUID>` directory, with no-follow opens, entry identity checks, and relative `unlinkat` operations. Linked app/Applications directories and mounted directories on another device are rejected. Descendant symlinks are unlinked rather than followed. Traversal is bounded to 128 nested folders and releases descriptors as it proceeds. This is ordinary file deletion, not secure erasure, and arbitrary concurrent external edits to app-owned directories are not supported. A detected change or filesystem error leaves the deletion pending for review.

## Windows-support packages

The native target reuses the repository's MiniZip sources through a small C wrapper and links the system zlib. Validation reads every entry in bounded chunks, checks decompression, sizes and CRCs, and verifies ZIP/ZIP64 directory bounds, paths, guest links, metadata, a 32-bit x86 ELF Wine launcher, and the presence of Wine's ntdll/kernel32 libraries. It extracts and executes nothing. The validator accepts stored and Deflate compression, with limits of 4 GiB per archive, 8 GiB expanded, 1 GiB per file, and 100,000 entries. Dependency-only packages, encrypted entries, unsupported native link/device records, and conflicting files are rejected. Identical short duplicates found in released filesystems retain the first entry, matching the emulator. Ordinary Boxedwine `.link` files resolve within the guest filesystem.

These are structural and integrity checks, not publisher authentication or proof that Wine's full dependency set and every Windows app will work. Runtime distribution still requires a trusted package and compatibility testing. A successful full scan is saved in a revisioned local receipt keyed by the ZIP’s SHA-256. Subsequent package checks, including after a restart and after copying to shared storage, hash the ZIP and reuse its validated metadata without decompressing every entry. Missing or unusable receipts trigger a full scan, and the build-time checker always runs full validation. The selected package’s checksum is checked at launcher startup; size, modification date, and file identity are checked before subsequent launches, with revalidation required after a detected change. Settings includes Check Again and reports Wine version, filesystem version, and the active source.

Settings → Choose Wine Version selects from the release XML list and downloads the exact package if needed before making it the library default. Apps with saved packages continue using their pinned Wine. The current default is shown explicitly in Settings. The earlier included/imported switching buttons were removed; all user selection goes through Choose Wine Version. Saved default references (`WindowsSupport/imported-wine.json`) and older included-package preferences (`WindowsSupport/use-included`) remain readable. A new choice is validated before changing the default. If the selected existing package fails validation, a usable alternative can be selected with an explanation in Settings. Changes to the library default are disabled while Windows apps run. Switching packages does not undo changes that Wine has already made inside an app's Windows environment; make an app backup before changing the library default. To try a version for one app, use a test copy as described below.

The build-time checker can also be run directly:


## Trying Wine versions for one app

All Wine choosers show the selected version’s download size before continuing, or “No Wine download needed” when an exact local package has been checked. Demo cards include required Wine in the total download size. These local checks do not contact a server; actions wait briefly while a package is being verified. If a local package changes after the notice, the app asks for a retry before downloading. See [Wine download disclosure](WINE_CATALOG.md) for the validation and reuse rules.

Choose **Try Another Wine Version…** in an app's details or context menu. Select a Wine version from the release list, give the copy a name, and choose **Create Test Copy**. The exact catalog package is downloaded if needed, verified, and pinned for the new app. The copy is ready for you to launch. The original app must be closed; the launcher blocks launches and library changes during copying.

Each test copy has a fresh app ID, independent Windows root, copied installer, original launch settings, and a reference to its exact shared Wine package. Library-default changes do not affect its selected version. The app details and App Settings show whether an app uses the library default or a pinned Wine version. The copy starts with no last-opened date or latest/previous launch logs, so an earlier run of the original is not presented as a test result.

The original app and its Wine reference are retained. A different Wine version can alter registry and prefix files when launched; switching back would not undo those changes. Creating a separate copy keeps the previous environment available. Saves and other changes do not synchronize. Keep the copy that works, rename it through App Settings, and use Removed Apps for the copy you no longer need. Test copies need space for their Windows files; identical Wine packages share storage, and older private ZIPs are excluded from the copy.

Copying uses the existing chunked, cancellable worker. The copied tree is checked against the original before pinning the chosen Wine package, and the original is checked again before completion. A failed or cancelled operation removes its new uncommitted copy; cleanup failures remain visible in Unfinished Work. Completed copies have the same verified restart recovery as other imports. Shared package references require library format 7 and recovery format 4; exported backups remain self-contained and compatible with the existing backup formats.

## App backups

Close the Windows app, then choose **Back Up App…** in its details or context menu. Choose **Add App → Restore App Backup…** (also in the File menu) to restore it. Restoration adds a new entry named “App (restored)” with a fresh ID; it never overwrites an existing app or launches the restored program automatically. Remove it through Removed Apps if it is no longer needed.

A `.boxedwinebackup` is an uncompressed Finder package containing `Manifest.json` and `Application/`. New exports also include a hidden `.BoxedwineExport` ownership marker for interrupted-export recovery; older backups remain supported. The package includes the complete writable root, registry, saves, hidden files, empty directories, the copied installer and launch log, launch settings, and a snapshot of the complete Wine filesystem ZIP at `Application/WindowsSupport/wine.zip`. This can make each backup large. Files mounted outside the owned app directory are not included, including folders used through Run Another Program → Choose File. Add App imports copy app and installer data into owned storage. Backups may contain personal Windows files and are not encrypted. Keep the entire package together when moving or storing it.

The manifest contains SHA-256 checksums and sizes for regular files, directory records, and normalized internal host links. Boxedwine verifies the copied tree and the Wine package before writing the manifest last. Restoration checks the selected package, copies it into a new private directory, verifies the copy again, and validates its Wine package before committing the library. Manifest paths are compared with enumerated paths, never used as copy destinations. Checks detect missing, extra, and changed contents; they do not authenticate the publisher of a backup. Unsupported formats, special files, and host links outside the tree are rejected. Limits are 100,000 tree entries, a 32 MiB manifest, and 4 KiB relative paths, plus the existing Wine-package limits. Mac file permissions and extended attributes are not preserved; this format backs up the Windows environment rather than a macOS filesystem image.

Export refuses to replace existing files or backups; choose a new name for each snapshot. Copying, hashing, and package validation run off the main actor and can be cancelled. The app being backed up cannot launch or change settings until export finishes. Cancellation and ordinary failures remove only the new partial copy. Quit waits for cleanup or a commit that has already started. A forced kill or power failure may leave an incomplete package without a manifest, which restoration rejects. Unfinished Work provides review and cleanup after the user selects that package again.

Restored entries and Wine test copies use a content-addressed `winePackage` reference and retain `savedWineVersion` for display and backup compatibility. They can launch without a library-default package and never silently fall back when the pinned package is missing or invalid. Successful validation is cached per package URL while its size/date/file identity remains unchanged. The first shared reference upgrades metadata to format 7 and saves the previous metadata before any private Wine duplicate is removed. Older launchers reject format 7. See [Shared Wine storage](SHARED_WINE.md) for migration, recovery, and collection rules.

The launcher uses the sandbox's user-selected read/write entitlement for native backup save panels. It retains the selected URL's security scope throughout each operation. The runtime's sandbox entitlements are unchanged.

## Interrupted work

New app-folder, installer, Wine-package, Wine-test-copy, backup-export, and backup-restore operations write an atomic record in `Operations/<UUID>.json` before copying. On launch, **Unfinished Work** reports leftover records; **Check Again** refreshes the list. Its sidebar entry and View-menu command appear only when records or a recovery-check error need attention, alongside the library's Review notice. Clearing the last item returns to All Apps and hides these entry points. A recheck keeps an existing error visible until the check succeeds. Recovery is explicit and never launches a Windows program or installer automatically.

A completed app copy records its metadata and a SHA-256 inventory before the library commit. **Finish Adding** rechecks the copied tree and any private Wine package, then adds it to the library. A copied installer is left ready for the user to run. An app already in the active library or Removed Apps is never offered for recovery or cleanup, including after a crash between saving the library and retiring its journal. A finished Wine copy is verified against its checksum (with full validation if no current receipt exists) before **Use Package** replaces the shared imported copy. A missing temporary copy offers cleanup of its reminder instead of completion.

Incomplete copies cannot be added. **Clean Up…** asks for confirmation before removing only the fixed app-ID directory or staged Wine ZIP belonging to the operation. Restart the import from the original source afterward; byte-level copy resumption is not implemented. Cleanup records its intent before removing files, retains that state if removal fails, and can be retried. Directory traversal uses open file descriptors, refuses linked app directories, and removes descendant symlinks without following them. The current shared `wine.zip` is never a staging-cleanup target.

For an interrupted export, **Locate Backup…** reacquires sandbox access through the native open panel. Cleanup requires both the saved directory identity and the matching ownership marker. Any package containing `Manifest.json` is kept, even if its manifest is damaged; the restore flow performs the complete contents check. A cleanup interrupted at the final empty-directory removal can be retried with its saved identity and cleanup intent, and refuses newly added contents. **Keep Files and Dismiss** removes only the reminder. Moving a backup to another volume, copying it, losing its marker, or interrupting creation before the ownership record is complete may prevent a match; those files remain for manual review.

Records are limited to 32 MiB, 100,000 inventory entries, and 1,024 files in the operations directory. Damaged or newer records are shown for manual review without changing their files. Recovery covers operations created by this preview; untracked orphan files from older previews are not automatically adopted or deleted. A journal is not a backup and does not guarantee survival of disk damage or lost filesystem writes.

## Process and rendering boundaries

```text
Boxedwine.app (SwiftUI / AppKit)
  library.json + per-app files
  Foundation Process + argv + stdin quit command
    Contents/Helpers/BoxedwineEngine.app
      Wine + emulator + SDL display/input + existing audio/graphics
```

The runtime is a nested application bundle so macOS can identify its windows separately. The launcher starts its executable directly, retaining process ownership and sandbox inheritance. It does not use a shell, `args.txt`, or the legacy ImGui launcher. Only one session may run against a given writable root at a time. Separate roots may run concurrently.

Installer selection results and prepared launches wait behind the current library operation. The launcher reloads saved metadata after both successful and failed operations before releasing these callbacks, so they cannot overwrite deletion markers, recovered apps, or partially applied Wine settings with an older library snapshot. A resumed launch rechecks its app and launch eligibility; Stop and shutdown cancel waiting launches. This coordination lives in the tested `LibraryOperationGate` component.

The runtime sends stdout and stderr to a shared pipe. A dedicated serial queue drains it into `Logs/latest.log`, retaining at most 2 MiB. When it fills, the oldest output is dropped and an omission marker is added. On the next launch, the bounded latest log replaces `Logs/previous.log`; only those two managed logs are retained. Existing unbounded logs are read with a size limit and shortened when rotated. The launcher drains available final output and appends the process exit code or terminating signal before notifying the UI. Disk-write errors stop log writes while output continues to drain, and are reported when the session ends. This is diagnostic logging, not a durable audit trail; a forced launcher exit can lose buffered output. The library shows an indeterminate **Launching…** indicator with a Stop button for each starting app or installer. A complete `Showing Window` line in that session’s live pipe clears the indicator and changes its status to **Running** or **Installer running**. Detection handles split reads and CRLF, reports only the first window, and remains independent of log trimming or disk-write errors. Stopping, a failed start, or process exit also ends the launching state; late output cannot overwrite the stopped or exited state. There is no guessed startup timeout. A shown window does not mean the guest has finished loading or passed a compatibility check.

The native runtime does not enable `BOXEDWINE_RECORDER`. The recorder-enabled executable returns code 1 on ordinary shutdown, which the launcher would otherwise interpret as a failure. The existing targets retain their recorder behavior. The native runtime's normal exit code indicates emulator shutdown, not a compatibility verdict or the guest program's exit code.

The launcher sends `quit\n` over stdin for a normal stop. Force Stop terminates only that child process. If the launcher disappears, EOF on the pipe terminates the runtime, preventing an orphaned session from continuing to modify its root.

## Launch troubleshooting

**View Launch Log…** offers Latest and Previous, a last-128-KiB preview, and **Save Log…** for a local snapshot of the full retained log (at most 2 MiB). Refresh updates a running app's snapshot. The native save panel holds access only for the save, and rejects destinations inside the app library. Nothing is uploaded. Logs can contain filenames, paths, arguments, and app output; the view asks users to review them before sharing. Restored backups retain their logs; new Wine test copies clear both managed logs so the original's sessions are not shown as test results.

An unexpected runtime exit adds a notice beside the app's launch controls, with direct access to its log. Failed preflight/launch attempts retain their concrete error in the same details pane. The log viewer explains how to check the selected program, adjust window settings, and try another Wine version in an independent copy. It does not infer compatibility from Wine warnings or a zero exit code. Session notices are kept for the current launcher session; retained logs survive restart. Log directory and file operations reject symbolic links, nonregular files, and multiply linked log files before replacing contents.

## Window presentation decision

Keep the existing contained desktop for this milestone. Consider a per-app choice between **Windows desktop** and **Separate Mac windows** after testing a small utility prototype with users. Games with fixed resolutions and fullscreen transitions benefit from retaining the contained mode; document apps and utilities are stronger candidates for independent host windows. These are product hypotheses to validate, not measured user preferences.

This decision is independent of both SDL replacement and process isolation. SDL can own multiple windows, and one runtime process can own several host windows. The native launcher should continue to manage a session rather than own its rendered guest windows.

The current code already provides useful boundaries:

- `source/x11/xserver.cpp`, `XServer::draw`: walks mapped root children and presents them on one screen.
- `source/x11/xwindow.cpp`, `XWindow::draw`: submits pixels with a window ID; transient relationships and reparenting are tracked separately.
- `platform/sdl/knativescreenSDL.cpp`: owns the SDL host window and desktop presentation.

A future presenter should map appropriate top-level guest windows to host windows and keep child controls within their parent. It must preserve transient ownership, popup behavior, stacking, focus and input grabs, coordinate transforms, resize notifications, DPI, and OpenGL/Vulkan drawable lifetimes. A one-to-one mapping of every X11 window would create incorrect host windows for controls and menus. Start with Notepad plus its dialogs; retain the desktop fallback while expanding compatibility.

This direction is consistent with Apple's emphasis on windows supporting multitasking, and fullscreen supporting focused game experiences: [Windows](https://developer.apple.com/design/human-interface-guidelines/windows) and [Designing for games](https://developer.apple.com/design/human-interface-guidelines/designing-for-games).
